# Ignopticon plan

Wildfire spread forecasting for NASA Space Apps 2026 ("Harmonization of MODIS and VIIRS Hot Spots"), displayed on a fork of cambecc's earth with a time scroll.

## Decisions already made
- **Event:** the 48-hour Space Apps event. Longer research comes afterward.
- **Region:** US only for now. Fuel and weather sources for other regions are a low-priority task.
- **Compute:** this machine (RTX 5090 32 GB, 16 cores, 60 GB RAM, ~750 GB free). UW Hyak's Tillicum (GPU cluster, H200s, $0.90/GPU-hour with 8 CPUs per GPU, first 100 h free) is available: account `elinzi`, $250 enforced budget to 2027-05-02 (~280 GPU-hours). The 48-hour plan still runs entirely here.
- **Goal:** predict where an already-burning fire spreads over 3–24 hours. Ignition risk is out of scope.
- **Engine:** ELMFIRE. It is Fortran/MPI and CPU-only, so forecasts use the 16 cores. The GPU is for post-event ML.
- **Claim to test:** ELMFIRE updated with VIIRS observations (B) beats plain ELMFIRE (A) against mapped perimeters. With one or two fires this is a case study, not a general result.
- **Suppression:** deferred until the uncorrected forecast is validated.
- **Display:** cambecc's earth (MIT): globe, color overlay, wind particles, URL-hash state. Modelling matters more than display.

## Before the event
First check the Space Apps rules on what preparation is allowed. Setup and data downloads are usually fine; writing project code is not.
1. Install GDAL (plus rasterio, GeoPandas) and wgrib2. gfortran and MPI are already installed.
2. Build ELMFIRE and run its tutorial case.
3. Time one 24-hour run of one ensemble member on the demo fire's area. That decides ensemble size (target: a full replay in about an hour on 16 cores).
4. Fork cambecc/earth and run it locally. **Done:** vendored in `earth/` (upstream commit 5f091f0, 2016-09-03). `cd earth && npm install && node dev-server.js 8080`, then open http://localhost:8080. Runs with only the bundled coastlines and 2014 sample wind; no fire data yet.
5. Pick the demo fire: needs HRRR (2014+), good VIIRS coverage, and timestamped airborne-infrared perimeters. Candidate: Caldor 2021.
6. Download: US FIRMS archive (MODIS C6.1 and VIIRS 375 m, keeping scan/track fields), LANDFIRE fuels and canopy plus 3DEP elevation for the fire's area, HRRR for the fire's dates, the perimeter sequence (NIFC/FIRIS; MTBS for final areas).

## Modelling steps
- **M0 Data pipeline:** FIRMS, LANDFIRE (FBFM40, canopy cover/height/base height/bulk density), 3DEP slope/aspect, HRRR (ERA5 for pre-2014), fuel moisture, perimeters. Keep fuel and weather loaders behind one interface so other regions only need new loaders.
- **M1 Fire selection:** split by whole fire into development and held-out sets.
- **M2 Baselines:** no-growth and wind-driven ellipse, then plain ELMFIRE (A).
- **M3 Fire state from hotspots:** detections → pixel footprints → union with burned area → ELMFIRE initial raster (`PHI_FILENAME`). Don't connect hotspots into a polygon. Ensemble of plausible states (grow/shrink unobserved edges).
- **M4 Updates at each satellite pass (B):** an observation model predicts which pixels should detect fire (front within footprint, FRP-dependent detection probability, view angle). A particle filter re-weights members and a few parameters (spread multiplier, wind bias, fuel moisture). GOES fills gaps between passes (optional).
- **M5 Learned correction (C, post-event, GPU):** R = R_phys · exp(f(X)); targets from arrival-time maps interpolated between perimeters.
- **M6 Evaluation:** IoU/F1, arrival-time error, Brier score and reliability at 3, 6, 12, 24 h. Forecasts use only data available at issue time.
- **M7 MODIS/VIIRS harmonization:** learn sensor differences from the 2012+ overlap (by FRP, land cover, season), aggregate onto a daily grid (e.g. 0.1°), extend back to 2000. Feeds the calendar and time scroll.
- **M8 Suppression (deferred):** ELMFIRE's built-in suppression first, then fuel removal and added moisture. Present as scenarios only.

These perimeters (and the FEDS archive's daily history) are the natural ELMFIRE starting perimeters and verification targets; NIFC WFIGS can add incident names.

More passes/satellites are just more downloads; leave bulk storage for the supercomputer.

"Now" still loads the current files. "Fire band night" has NOAA-21's night passes for both days (Aug 2 05:24-10:42Z, Oct 29 06:12-11:30Z; ~2-2.8 GB raw, ~175 MB tiles each): fires a median +34 K (Aug 2, 7,117 detections) and +25 K (Oct 29) above ground 3 km away. I4's Out_of_Range flag means a folded-over fire by day but mostly cloud tops too cold for the band at night (I5 ~200 K), so flagged pixels are fires only if I5 > 270 K, else set to the scale's minimum. `viirs_i4_tiles.py` now takes the DATE, and records the swath times in `info.json`, which the layers panel shows.
- **Done:** heat frames, the start of M3/M4. `scripts/fire_observations.py` combines every heat source for one fire onto a 375 m grid, per overpass: VIIRS detections from S-NPP, NOAA-20 and NOAA-21 (their FRP), NOAA-21's fire band read from the raw L1B granules (pixels 5 K and 3.5 robust σ above an ~8 km background become FRP by the MIR method; the tiles can't be used, as they mosaic overlapping passes), and FEDS perimeters at every 12 h snapshot. It writes the observed frames and a fire-state raster (arrival = first pass seen hot, else midway between FEDS snapshots). `scripts/heat_frames.py` is the observation operator: any run's `time_of_arrival_*.tif` (s since issue) and optional `flin_*.tif` (kW/m), ELMFIRE's output names and units (its unburned value is undocumented; nodata or negative is treated as unburned), become heat release (HPA = flin/ROS, 30% smouldering with a 2 h decay), FRP (radiative fraction 0.146), and I4 brightness in that overpass's pixel footprint; cells ≥10 K above background are predicted detections. Each overpass after issue is scored (CSI, one cell of offset allowed), plus IoU with later FEDS perimeters. Earth's "Heat frames" layer steps or plays the overpasses: observed cells filled by FRP, a chosen run's predicted detections outlined. Until ELMFIRE is built, `scripts/ellipse_spread.py` (M2 wind-ellipse baseline, FBP length-to-breadth, GFS 10 m wind, constant head ROS; 0 = no growth) writes ELMFIRE-named outputs. Widemouth 2 (UT), issued 2026-08-02 12Z, scored on the 4 afternoon overpasses: head ROS 0.02 m/s CSI 0.30 (IoU 0.68 at Aug 3 00Z), 0.05: 0.22 (0.64), 0.1: 0.11 (0.57), no growth: 0.00 (0.66). Perimeter IoU hardly separates the runs; overpass heat does. Model FRP is ~20x below observed while detection counts match, so HPA, flaming and smouldering constants need fitting (M4). The fire band adds 14-61 cells per NOAA-21 pass beyond the detections, ~1% of the FRP.
- **Done (event day 1, 2026-11-14):** ELMFIRE runs here. Built from source (`tools/elmfire`, gitignored, upstream f4927b7, `build/linux/make_gnu.sh fast`, ~1 min). No GDAL install: `scripts/elmfire_case.py` writes ELMFIRE's ENVI .bsq/.hdr inputs through rasterio, and `scripts/gdal_shim/` stands in for the four GDAL tools ELMFIRE shells out to (gdalinfo, gdalsrsinfo, gdaltransform, gdal_translate); put it on the PATH. Tutorial 01 reproduces (start (0, 3000), runs south, L/B 1.7, 9,823 acres in 5.5 h). Widemouth 2 inputs: `scripts/landscape_download.py` (LANDFIRE LF2025 FBFM40/CC/CH/CBH/CBD + 3DEP via ImageServer, tiled requests, 37.5 m = the state grid ×10, slope/aspect by Horn) and `scripts/hrrr_weather.py` (HRRR 12Z run f00-f24 by byte range from AWS, 20-ft wind = 10 m × 0.87, grid-relative winds rotated to true north (HRRR's lon_0 is 262.5: normalise it), dead moisture from Simard EMC). One 24 h member on the 1,600² grid takes 4 min on one core, so 16 cores do ~4 members/min (a 200-member ensemble in under an hour). The uncalibrated base run overpredicts: 904 km² at Aug 3 00Z vs FEDS 363 (IoU 0.39), overpass CSI 0.04-0.10, while its FRP is now the right order (91-110 GW vs 7-42 GW observed; the ellipse was 20x low).

## Compute
- One entry point per ensemble member: `scripts/run_member.sh MEMBER_DIR`. Locally `scripts/run_ensemble.sh` (`xargs -P16`); on Tillicum one job, `hyak/tillicum.slurm`, runs the same `run_ensemble.sh` on the CPUs that come with its GPUs and scores the members (a klone-style array, `hyak/ensemble.slurm` + `hyak/score.slurm`, would pay a GPU hour per one-core member). Members are made by `scripts/make_ensemble.py` (a grid of settings; engines `ellipse` and `elmfire`, the latter a template `elmfire.data` with namelist overrides), are skipped once done (so preempted arrays can be resubmitted), and are scored by `heat_frames.py`. Software comes from one image, `hyak/Containerfile`: ELMFIRE, GDAL tools, Python packages; podman here, Apptainer on Hyak. Not built yet. See `hyak/README.md`. Tested here: 14 ellipse members (head ROS 0-0.1 m/s × HPA 4000/8000 kJ/m²) in 44 s on 16 cores; best 0.02 m/s, 4000 kJ/m² (CSI 0.32), while model FRP stays ~20x low at either HPA.
- **Requirements:** our scripts need no GDAL install or wgrib2. rasterio's pip wheel bundles GDAL; GRIB goes through pygrib. ELMFIRE needs gdal_translate only to convert its outputs to GeoTIFF (avoidable with `CONVERT_TO_GEOTIFF = .FALSE.`, reading the BIL with rasterio). Preparing its LANDFIRE/3DEP inputs (clip, reproject) can be done with rasterio. wgrib2 would only help subset HRRR, which pygrib or byte-range downloads also handle.
- GPU after the event: M5 training; optionally a GPU spread model for large ensembles, checked against ELMFIRE first.
- Tillicum: M5 training and any GPU spread model on H200s (its strength); ELMFIRE ensembles too big for here (a full node is 64 cores, $7.20/h, 4x this machine). First check login, group, project path, and whether GPU-less jobs are allowed and how they're billed (hyak/README.md).
